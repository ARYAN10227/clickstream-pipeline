# Performance: integer timestamps to ClickHouse

**Change** (commit `perf(consumer): pass timestamps to ClickHouse as epoch-ms ints`):
`to_row` now hands `event_time` and `produced_at` to clickhouse-connect as integer epoch
milliseconds instead of building `datetime` objects. For `DateTime64(3)` columns the driver
writes ints directly as ticks, so the `datetime` round trip that the
[profile](profile-notes.md) showed (`_datetime64_ticks` 8.2% + `ms_to_datetime` 4.3% of
consumer main-thread time) is gone. The e2e-latency metric now reads `produced_at` as ms.
Stored data is unchanged: a check on the "after" run's 6,000,000 rows found every
`event_time` in the run's 300 s window, none in the wrong year and none with
`produced_at` before `event_time`.

All runs: 1 consumer replica, 1 producer process, same machine (cloud VM, Intel(R) Xeon(R)
Processor @ 2.10GHz, 4 vCPUs, 15.7 GiB RAM, shared by Redpanda, ClickHouse, the consumer,
Prometheus, Grafana and the load generator). Every number is copied from the linked result
files.

## Before vs after at 20,000 events/s for 300 s

| run | load | achieved produce rate (events/s) | events sent | consumer throughput (events/s) | max lag | p50 / p95 / p99 / max (ms) | throughput / p99 target |
|---|---|---|---|---|---|---|---|
| [`20261019T195118`](bench-20261019T195118.md) | 20,000/s x 300 s | 20,000.0 | 6,000,000 | 20,051.1 | 8,564 | 230.0 / 353.0 / 391.0 / 993 | PASS / PASS |
| [`20261019T201001`](bench-20261019T201001.md) | 20,000/s x 300 s | 20,000.0 | 6,000,000 | 20,031.7 | 9,927 | 209.0 / 327.0 / 381.0 / 779 | PASS / PASS |

- **Latency improved slightly:** p50 230.0 -> 209.0 ms, p95 353.0 -> 327.0 ms, p99 391.0 -> 381.0 ms,
  max 993 -> 779 ms.
- **Throughput did not change measurably, and cannot at this load:** at 20,000 events/s the
  consumer only has 20,000 events/s to process, so consumer throughput
  (20,051.1 before, 20,031.7 after) is capped by the input rate in both runs. Max lag was
  8,564 before and 9,927 after; at this load, lag is dominated by batching, not by consumer speed.
- The CPU saving predicted from the profile (about 12.5% of main-thread time) was not
  measured directly: the consumer was not re-profiled after the change.

**Excluded run.** [`20261019T200423`](bench-20261019T200423.md) (same code as "after") is kept but is **not a valid
measurement**. It started with a backlog of 305,000 messages left over from the profiling run,
and the consumer was not assigned partitions for about the first 25 s (lag grew by about
100,000 per 5 s) while the profiling consumer's group session timed out. That gave max lag
802,203 and p99 31,256.9 ms; it says nothing about the change. The "after" run was
re-done from lag 0 with a single group member.

## Headroom: 30,000 events/s for 120 s (after the change)

| run | load | achieved produce rate (events/s) | events sent | consumer throughput (events/s) | max lag | p50 / p95 / p99 / max (ms) | throughput / p99 target |
|---|---|---|---|---|---|---|---|
| [`20261019T201529`](bench-20261019T201529.md) | 30,000/s x 120 s | 29,997.5 | 3,600,000 | 30,025.8 | 22,844 | 246.0 / 495.0 / 634.0 / 838 | FAIL / PASS |

One producer process reached the rate (29,998 events/s), so `--procs 2` was not needed.
**The consumer kept up at 30,000 events/s:** throughput 30,025.8 events/s, max lag 22,844,
drained to 0, p99 634.0 ms. The throughput target shows FAIL only because the SPEC target requires
300 s and this run was 120 s; the p99 target passed. There is **no 30,000 events/s run of the
code before the change**, so this headroom cannot be attributed to the change. It shows
capacity after the change, not a before/after difference.
